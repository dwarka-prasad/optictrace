# Contributing to OpticTrace

Thanks for helping build OpticTrace! This guide gets you productive quickly.

## Development setup

```bash
make setup      # dependencies, dashboard, binaries — start here
make dev        # agent + mock upstream + seeded traffic, dashboard on :9095
make help       # every target
```

`make dev` leaves a stack running with traffic already in it: several tenants
across regions and plans, redacted payment secrets, a metered AI route, an
ungoverned route, 4xx/5xx and slow calls, and one correlated trace. Rules you
cannot see firing are rules you cannot tell are broken, so the seeded traffic
deliberately covers every mechanism in `optic.yaml`.

| | |
|---|---|
| `make test` / `make test-all` | root module / **every** module, including the satellite ones |
| `make rules` | governance assertions in `optic.test.yaml` |
| `make lint` | `go vet` + gofmt check |
| `make seed` | more traffic into an already-running agent |
| `make fixture` | regenerate `examples/traffic-sample.jsonl` |
| `make bench` | interceptor overhead vs a bare handler |

Run `make test-all`, not `make test`, before pushing. The examples and SDKs are
separate Go modules, so `go test ./...` in the root does not compile them — and
they are exactly what breaks when a shared type like `ext.Filter` gains a field.

Individual pieces, if you need them:

```bash
# Dashboard against a running agent (dev server on :3000, agent on :9095)
cd ui && npm install && npm run dev

# SDKs
cd sdks/express && npm install && npm test
cd sdks/fastapi && python3 test_middleware.py
cd sdks/gin && go test ./...

# The example applications — each starts a real stack and asserts against it
cd examples/python-shop  && ./run.sh && .venv/bin/python verify.py   # 25 checks
cd examples/lead-pipeline && ./run.sh && python3 verify.py           # 19 checks
```

The examples are where end-to-end claims get checked. `sdks/fastapi` shipped for
weeks delivering **zero** records — its timestamps were rejected by the agent and
the failure was swallowed — because nothing ran the SDK against a live agent.
If you change an SDK, run its example.

### The traffic fixture

`examples/traffic-sample.jsonl` is what the governance PR bot reviews every
pull request against, and it is generated by `make fixture` rather than edited
by hand — a hand-written fixture keeps whatever fields existed the day someone
typed it, so the bot quietly stops exercising everything added since. It is
produced against `deploy/compose/optic.yaml`, the same config the workflow
reviews with, so the rules and the traffic cannot drift apart. Regenerate it
whenever you add a rule mechanism or a record field.

## Ground rules

1. **Governance invariants are non-negotiable.** Proxied traffic is never
   mutated; redaction/restriction applies only to recorded telemetry; the
   telemetry pipeline must never block or fail a request. Any PR that could
   leak a restricted or redacted value needs a test proving it doesn't.
2. **The rule engine is portable.** `internal/engine` (Go),
   `sdks/express/engine.js`, and `sdks/fastapi/.../engine.py` must stay
   semantically identical. If you change matching or redaction semantics,
   change all three and their parity tests.
3. **Hot path discipline.** Per-request work in `internal/proxy` should not
   allocate beyond the policy/record. Benchmark if in doubt.
4. **Config changes are schema changes.** New `optic.yaml` fields need:
   strict validation, defaults in `applyTelemetryDefaults`/`Parse`, docs in
   the README reference, and a validation test.

## Pull requests

- Fork, branch from `main`, keep PRs focused.
- `go vet ./... && gofmt -l . && go test ./...` must pass; UI changes need `npm run build` to succeed.
- Add tests for behavior changes; update docs in the same PR.
- Use conventional commit prefixes when convenient (`feat:`, `fix:`, `docs:`).

## Reporting issues

Use the issue templates. For **suspected telemetry leaks** (sensitive data
appearing in logs/store/metrics despite rules), please email the maintainers
instead of opening a public issue — treat it as a security report.

## What to work on

Open work lives in the [issue tracker](https://github.com/dwarka-prasad/optictrace/issues).
Issues carry an `area:` label so you can find the part of the system you want to
touch, and anything tagged
[`good first issue`](https://github.com/dwarka-prasad/optictrace/labels/good%20first%20issue)
is scoped to be completable without knowing the whole codebase.

Each issue states what is true today with a file reference, so you can confirm
the problem still exists before writing anything.

## Releasing

Tagging `vX.Y.Z` triggers `.github/workflows/release.yml`, which runs the tests
and governance assertions, builds signed archives with goreleaser, publishes a
multi-arch image, and updates the Homebrew tap.

The tap step needs a repository secret named `HOMEBREW_TAP_TOKEN` — a token with
push access to `dwarka-prasad/homebrew-tap`. The default `GITHUB_TOKEN` cannot be
used, since it is scoped to this repository only. If the secret is absent the
step no-ops and notes it in the job summary rather than failing the release, so
the formula can also be regenerated by hand:

```bash
./scripts/update-tap.sh v0.7.0
```

The script hashes the release's own published `checksums.txt`, so it must run
after the release exists, and the formula can never claim a hash that differs
from the artifact a user downloads.
